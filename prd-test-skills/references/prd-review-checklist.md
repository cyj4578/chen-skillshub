# PRD 文档审查清单

> 本清单用于把 PRD 从“写了什么”审到“能否开发、能否测试、能否上线、上线后会不会出事故”。检查时必须结合场景穷举、专项清单和测试用例反推。

---

## 一、结构完整性（10项）

### 1.1 章节存在性检查

| # | 检查项 | 通过标准 | 漏洞类型 |
|----|--------|----------|----------|
| S01 | 文档封面 | 包含标题、编号、版本、作者、日期 | 缺失信息 |
| S02 | 修订历史 | 包含版本变更记录 | 不可追溯 |
| S03 | 问题陈述 | 有明确的背景和问题描述 | 需求无依据 |
| S04 | 目标 | 有3-5个可量化的目标 | 目标模糊 |
| S05 | 非目标 | 明确列出排除范围 | 范围蔓延 |
| S06 | 用户故事 | 按角色和优先级分组 | 场景遗漏 |
| S07 | 需求详情 | 包含FR和NFR | 功能缺失 |
| S08 | 成功指标 | 区分领先和滞后指标 | 无法衡量 |
| S09 | 时间计划 | 包含关键里程碑 | 进度失控 |
| S10 | 依赖与风险 | 有依赖方和风险识别 | 执行受阻 |

## 二、业务真实性（6项）

| # | 检查项 | 通过标准 | 漏洞类型 |
|----|--------|----------|----------|
| B01 | 问题有证据 | 有数据、用户反馈、业务损失或历史案例支撑 | 伪需求 |
| B02 | 受影响对象明确 | 明确用户群体、业务方、角色规模和影响范围 | 对象不清 |
| B03 | 当前基线明确 | 有当前值、历史值或现状描述 | 无法比较 |
| B04 | 收益与成本匹配 | 预期收益、投入成本、机会成本基本匹配 | 投入失衡 |
| B05 | 优先级有理由 | P0/P1/P2 的排序有业务、风险或依赖依据 | 优先级随意 |
| B06 | 替代方案被比较 | 说明为什么不采用更低成本方案 | 方案武断 |

## 三、逻辑一致性（8项）

### 2.1 目标-指标一致性

| # | 检查项 | 通过标准 | 漏洞类型 |
|----|--------|----------|----------|
| L01 | 目标可衡量 | 每个目标有明确的数值指标 | 无法评估 |
| L02 | 指标可追踪 | 有数据来源和计算方法 | 指标悬空 |
| L03 | 指标值合理 | 目标值有依据（如行业基准、历史数据） | 指标虚高 |

### 2.2 需求链条一致性

| # | 检查项 | 通过标准 | 漏洞类型 |
|----|--------|----------|----------|
| L04 | US→FR 覆盖 | 每个US至少有一个FR对应 | 功能缺失 |
| L05 | FR优先级对应 | FR优先级与US优先级一致 | 优先级错配 |
| L06 | 验收标准覆盖 | 每个FR有具体的验收标准 | 验收模糊 |
| L07 | 指标与目标对应 | 成功指标能反映目标达成 | 指标偏离 |

### 2.3 非目标合理性

| # | 检查项 | 通过标准 | 漏洞类型 |
|----|--------|----------|----------|
| L08 | 非目标有理由 | 每个非目标有排除原因说明 | 随意排除 |

## 四、场景完整性（14项）

### 3.1 用户故事完整性

| # | 检查项 | 通过标准 | 漏洞类型 |
|----|--------|----------|----------|
| R01 | 角色覆盖 | 主要用户角色都有US | 角色遗漏 |
| R02 | 场景覆盖 | 核心场景（正常/异常/边界/并发/中断）都有US | 场景缺失 |
| R03 | 价值明确 | 每个US明确说明用户获得的业务价值 | 价值模糊 |

### 3.2 功能需求完整性

| # | 检查项 | 通过标准 | 漏洞类型 |
|----|--------|----------|----------|
| R04 | 交互流程完整 | 涉及前后端的功能都有描述 | 流程断点 |
| R05 | 状态定义 | 涉及状态机的功能有状态定义 | 状态遗漏 |
| R06 | 异常处理 | 关键流程有异常场景描述 | 容错缺失 |
| R07 | 边界条件 | 空值、最大/最小值、临界时间、极端数量有处理 | 边界遗漏 |
| R08 | 并发冲突 | 多人/多请求同时操作有规则 | 并发缺陷 |
| R09 | 中断恢复 | 断网、刷新、退出、登录失效、服务失败有恢复策略 | 恢复缺失 |
| R10 | 逆向误操作 | 撤销、取消、重复提交、误删、误配置有处理 | 误操作风险 |
| R11 | 跨端一致性 | 小程序/H5/App/PC/后台状态展示一致 | 多端错乱 |
| R12 | 跨角色协作 | 用户、运营、客服、管理员等协作边界清楚 | 协作断点 |
| R13 | 跨系统链路 | CRM、订单、支付、库存、消息等系统边界清楚 | 系统断链 |
| R14 | 历史兼容 | 存量数据、老用户、旧版本、迁移规则有说明 | 兼容遗漏 |

## 五、数据与权限（10项）

| # | 检查项 | 通过标准 | 漏洞类型 |
|----|--------|----------|----------|
| DP01 | 埋点事件 | 核心曝光、点击、提交、成功、失败事件定义清楚 | 数据缺失 |
| DP02 | 事件字段 | 关键字段、枚举、ID、来源、时间戳定义清楚 | 字段不清 |
| DP03 | 指标口径 | 指标公式、去重、归因、统计周期明确 | 口径争议 |
| DP04 | 数据来源 | 明确来自埋点、业务库、报表、人工统计或第三方 | 来源悬空 |
| DP05 | 数据延迟 | 明确实时、T+1、离线或人工更新时间 | 延迟误判 |
| DP06 | 数据权限 | 不同角色可见、可导出、可操作的数据范围明确 | 越权风险 |
| DP07 | 操作权限 | 查看、新增、编辑、删除、审批、导出权限明确 | 权限缺失 |
| DP08 | 敏感信息 | 手机、身份证、医疗、财务等信息有脱敏和最小化原则 | 隐私风险 |
| DP09 | 审计日志 | 关键配置、审批、删除、导出有操作日志 | 不可追溯 |
| DP10 | 防滥用 | 频控、防刷、防重复提交、防越权策略明确 | 滥用风险 |

## 六、可测试性（7项）

| # | 检查项 | 通过标准 | 漏洞类型 |
|----|--------|----------|----------|
| T01 | 验收标准可验证 | 标准是「是/否」可判断的 | 验收主观 |
| T02 | 验收标准可重复 | 同一标准多次测试结果一致 | 标准模糊 |
| T03 | 验收标准有条件 | 明确前置条件和环境要求 | 场景不清 |
| T04 | 指标可计算 | 成功指标有明确的数据来源和公式 | 指标悬空 |
| T05 | 时间计划可验证 | 里程碑有明确的交付物定义 | 交付模糊 |
| T06 | 用例可反推 | 每个核心FR能反推出测试用例 | 无法测试 |
| T07 | 失败可判断 | 说明何种情况判为失败、阻塞或需回滚 | 失败标准缺失 |

## 七、风险与上线完整性（9项）

| # | 检查项 | 通过标准 | 漏洞类型 |
|----|--------|----------|----------|
| D01 | 依赖已确认 | 所有依赖方都有确认或负责人 | 依赖悬空 |
| D02 | 风险可应对 | 每个风险有明确的应对措施 | 风险裸奔 |
| D03 | 开放问题有时限 | 开放问题有期望答复时间 | 问题无期 |
| D04 | 开放问题有负责人 | 每个问题有明确的负责人 | 责任不清 |
| D05 | 灰度策略 | 明确灰度范围、放量节奏、观察指标 | 上线失控 |
| D06 | 回滚策略 | 明确回滚条件、回滚步骤、数据处理方式 | 不可回滚 |
| D07 | 运营准备 | 客服话术、运营配置、门店培训、公告通知有安排 | 运营断点 |
| D08 | 合规审查 | 涉及医疗、金融、广告、隐私、未成年人等有合规判断 | 合规风险 |
| D09 | 监控告警 | 核心链路、接口、任务、数据异常有监控告警 | 不可观测 |

## 八、严重等级判定细则

| 等级 | 典型触发条件 |
|------|--------------|
| P0 | 资损、隐私泄露、严重合规风险；核心链路无法闭环；需求无法开发或验收；关键状态/金额/权限规则缺失 |
| P1 | 核心异常、边界、并发、依赖、灰度、回滚缺失；指标口径影响业务决策；跨团队职责不清导致排期不可控 |
| P2 | 非核心场景遗漏；状态、数据、角色、提示、操作日志不完整；存在返工或线上缺陷风险 |
| P3 | 文案、格式、示例、说明顺序、可读性优化 |

判级时按“最坏合理后果”而不是“当前文档篇幅”判断。若一个问题同时命中多个等级，取最高等级。

## 九、快速检查表（简化版）

适用于时间有限的快速审查：

```
【必查 - 结构】
☐ 封面信息完整（标题/编号/版本/作者/日期）
☐ 问题陈述有数据支撑
☐ 目标可量化（数值指标）
☐ 有明确的非目标定义

【必查 - 逻辑】
☐ US → FR 有对应关系
☐ FR 有验收标准
☐ 成功指标能衡量目标

【必查 - 完整性】
☐ 核心用户角色都有US
☐ 正常/异常/边界/并发/中断流程有描述
☐ 开放问题有负责人

【必查 - 数据权限】
☐ 核心埋点、指标口径、数据来源明确
☐ 查看/编辑/删除/导出/审批权限明确
☐ 敏感信息、审计日志、合规风险明确

【必查 - 上线】
☐ 灰度、回滚、监控、运营准备明确
☐ P0/P1问题能反推出测试用例
```

## 十、审查深度模式

| 模式 | 适用场景 | 检查项数 | 耗时 |
|------|----------|----------|------|
| 快速 | 时间紧迫，30分钟审查 | 基础结构 + 核心链路 + P0/P1风险 | ~30min |
| 标准 | 常规评审 | 全量检查清单 + 场景穷举 | ~1-2h |
| 深入 | 重大需求，多轮迭代 | 全量检查 + 专项清单 + 测试用例矩阵 + 上线推演 | ~2-4h |
