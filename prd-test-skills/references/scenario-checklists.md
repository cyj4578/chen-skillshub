# 场景穷举与专项清单

> 用于把 PRD 从主流程描述推演成可测试、可上线、可运营的完整场景。审查时不要只问“有没有写”，要问“如果这里失败、冲突、越权、回滚，会发生什么”。

---

## 一、通用场景穷举框架

对每个核心功能需求（FR）至少检查以下 8 类场景：

| 场景类型 | 必问问题 | 常见遗漏 |
|----------|----------|----------|
| 正常路径 | 用户按预期完成时，每一步输入、输出、状态变化是什么 | 只写页面，不写状态/数据 |
| 异常路径 | 接口失败、参数错误、依赖不可用时如何提示和恢复 | 失败后无兜底 |
| 边界条件 | 空值、0、最大值、最小值、临界时间、极端数量如何处理 | 临界规则缺失 |
| 并发冲突 | 多人、多端、多请求同时操作同一资源时谁生效 | 重复提交、超卖、状态覆盖 |
| 中断恢复 | 断网、刷新、退出、登录失效、支付中断后如何恢复 | 用户以为成功但实际失败 |
| 逆向误操作 | 取消、撤销、删除、重复点击、填错、选错能否纠正 | 不可逆误操作 |
| 跨角色协作 | 用户、运营、客服、管理员、财务、门店人员各自看到什么 | 协作断点 |
| 跨端/跨系统 | 小程序/H5/App/后台/CRM/订单/支付/消息系统是否一致 | 状态不同步 |

如果某个 FR 无法用以上框架反推出测试点，说明 PRD 不具备可测试性。

## 二、状态机审查清单

涉及订单、预约、审批、直播、退款、任务、排队、库存等状态型需求时，必须检查：

| 检查项 | 必须明确 |
|--------|----------|
| 状态列表 | 全部业务状态、系统状态、异常状态 |
| 初始状态 | 谁在什么条件下创建，初始值是什么 |
| 终态 | 成功终态、失败终态、取消终态、超时终态 |
| 流转条件 | 触发动作、触发角色、前置条件、后置结果 |
| 可逆性 | 哪些状态可撤销、可重试、可回退，哪些不可逆 |
| 超时规则 | 多久超时，超时后状态如何变化，是否通知 |
| 权限规则 | 每个状态下谁能看、谁能改、谁能推进 |
| 数据影响 | 状态变化对库存、订单、支付、统计、通知的影响 |
| 展示规则 | 前端、后台、报表、消息中的状态文案是否一致 |

缺少状态流转图或状态表时，状态型核心需求通常至少判 P1。

## 三、数据与指标审查清单

数据类、增长类、运营类、管理后台类 PRD 必查：

- 关键事件：曝光、点击、提交、成功、失败、取消、重试。
- 事件字段：用户ID、门店ID、订单ID、活动ID、来源、渠道、时间、状态。
- 指标口径：分子、分母、去重规则、统计周期、归因窗口。
- 数据来源：埋点、业务库、第三方、人工录入、离线任务。
- 数据延迟：实时、准实时、T+1、手动刷新。
- 数据权限：谁能看、谁能导出、是否脱敏。
- 数据质量：重复、漏报、延迟、脏数据如何识别。
- 看板消费方：谁用这个指标做什么决策。

若成功指标没有数据来源和公式，不能判为通过。

## 四、权限、安全与合规审查清单

涉及后台、用户数据、交易、医疗、财务、客户资产时必查：

- 角色：普通用户、员工、店长、运营、客服、财务、管理员、系统管理员。
- 操作：查看、新增、编辑、删除、审批、导出、配置、上下架、退款。
- 数据范围：本人、本门店、本区域、全公司、指定组织。
- 越权风险：URL直访、接口越权、跨门店访问、越级审批。
- 敏感信息：手机号、身份证、病历、交易金额、客户画像、定位。
- 审计日志：谁在何时对什么对象做了什么操作，操作前后值是什么。
- 防滥用：频控、防刷、防重复提交、防批量导出、防恶意配置。
- 合规：隐私授权、医疗广告、金融资质、未成年人、内容审核。

涉及敏感数据但无权限、脱敏、审计说明，通常至少判 P1；可能泄露隐私或产生合规事故时判 P0。

## 五、上线、灰度与回滚审查清单

上线前必须确认：

| 检查项 | 必须明确 |
|--------|----------|
| 灰度范围 | 哪些用户、门店、地区、流量比例先上线 |
| 放量节奏 | 每阶段观察多久，达到什么条件继续放量 |
| 观察指标 | 成功率、失败率、转化、投诉、接口耗时、错误量 |
| 回滚条件 | 哪些指标异常必须回滚 |
| 回滚步骤 | 前端、后端、配置、数据、定时任务如何恢复 |
| 数据处理 | 已产生订单、预约、状态、通知、埋点如何处理 |
| 运营准备 | 客服话术、后台配置、培训、公告、FAQ |
| 监控告警 | 谁收到告警，多久响应，如何升级 |

核心功能没有灰度和回滚策略，通常至少判 P1。

## 六、行业/类型专项清单

### 交易、订单、支付、退款

- 价格、优惠、税费、运费、尾款、抹零规则是否清楚。
- 库存扣减时机：下单、支付、锁定、取消、超时释放。
- 支付中断、重复支付、支付成功但订单失败如何处理。
- 退款、部分退款、原路退回、退款失败、对账差异如何处理。
- 订单状态与支付状态、发货状态、服务状态是否解耦。
- 资损风险、对账、审计、财务报表是否覆盖。

### 直播、活动、预约、挂品

- 预告、预约、开播、停播、回放、下播状态是否清楚。
- 多场直播、多门店、多主播、多场地冲突如何处理。
- 商品挂载、上下架、库存、价格、优惠在直播中如何同步。
- 用户预约、提醒、进入直播、下单、归因链路是否闭环。
- 违规内容、禁播、回放删除、评论管控如何处理。
- 直播数据：曝光、预约、观看、互动、成交、转化归因是否明确。

### 内容、审核、评论、消息

- 发布、编辑、删除、撤回、恢复、审核状态是否明确。
- 机器审核、人工审核、申诉、举报、处罚规则是否明确。
- 通知触达时机、模板、频率、失败重试、退订规则是否明确。
- 内容版权、违规词、敏感内容、用户隐私是否审查。

### 后台、权限、配置、审批

- 批量操作、误操作恢复、审批驳回、撤销、重新提交是否明确。
- 配置生效范围、生效时间、失效时间、历史版本是否明确。
- 删除/下线是否影响存量数据、历史报表、前台展示。
- 管理员权限是否过宽，是否需要二次确认或审批。

### 数据看板、报表、归因

- 指标定义、筛选条件、时间范围、导出权限是否明确。
- 数据刷新频率、延迟、失败、补数机制是否明确。
- 同一指标在多个页面是否口径一致。
- 归因规则是否处理多渠道、多触点、跨天、跨设备。

### AI、推荐、自动化

- 输入来源、输出结果、置信度、失败兜底是否明确。
- 误判、幻觉、偏见、越权生成、敏感信息泄露如何处理。
- 是否有人审、可撤回、可解释、可反馈、可追踪。
- 自动动作是否需要人工确认，是否能回滚。

## 七、审查者反问清单

审查结论前必须至少过一遍这些问题：

- 如果这个功能被恶意用户使用，最坏结果是什么？
- 如果这个功能被运营误配置，是否会影响所有用户？
- 如果依赖系统失败，用户看到什么，数据怎么恢复？
- 如果两个角色同时操作同一对象，谁的结果生效？
- 如果指标上线后很好看，是否可能只是口径造成的假象？
- 如果指标上线后很差，是否能定位是产品、运营、渠道还是技术问题？
- 如果上线当天要回滚，哪些状态和数据会残留？
- 如果客服接到投诉，是否能从后台查到原因并处理？
- 如果用户要求删除、导出、撤回或申诉，系统是否支持？
- 如果这个需求延期，哪些能力可以保留，哪些必须砍掉？

PRD 没有回答高风险反问时，应在报告中列为“待补充假设/开放问题”，不能默认为安全。

## 八、测试用例反推模板

| 字段 | 说明 |
|------|------|
| 用例ID | TC-模块-编号 |
| 关联需求 | US/FR/验收标准编号 |
| 场景类型 | 正常/异常/边界/并发/中断/权限/数据/兼容 |
| 前置条件 | 环境、账号、数据、状态 |
| 操作步骤 | 用户或系统动作 |
| 测试数据 | 输入值、边界值、异常值 |
| 预期结果 | 页面、接口、状态、数据、通知、日志 |
| 优先级 | P0/P1/P2 |

每个 P0/P1 问题必须能写出失败用例；写不出用例时，说明问题描述还不够具体。
