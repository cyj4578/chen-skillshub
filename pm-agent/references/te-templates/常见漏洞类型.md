# 常见 PRD 漏洞类型与案例

> 本文档整理了PRD文档中最常见的漏洞类型，提供识别方法和修复建议。

---

## 一、结构性漏洞

### 1.1 问题陈述缺失或不清晰

**识别特征**：
- 没有数据支撑，只有「用户需要」「我们认为」
- 问题描述模糊，如「体验不好」「效率低下」
- 缺少受影响用户群体的定义

**案例**：
```markdown
❌ 错误示例：
用户希望有更好的排队体验，需要开发取号功能。

✅ 正确示例：
目前顾客到店后需在前台人工登记排队，效率低下。
根据调研，约有35%的顾客因等待时间不确定而放弃等候，
导致日均流失客流约50人次。
```

**修复建议**：
- 增加量化数据（用户数、转化率、损失估算）
- 明确受影响用户群体
- 说明问题产生的业务影响

---

### 1.2 目标不可衡量

**识别特征**：
- 使用「提升」「改善」「优化」等模糊词
- 没有具体数值指标
- 目标与业务目标无关联

**案例**：
```markdown
❌ 错误示例：
- 提升用户体验
- 降低用户流失率
- 改善系统性能

✅ 正确示例：
- G-01: 用户平均取号耗时 ≤ 15秒（当前45秒）
- G-02: 放弃等候率降低至15%（当前35%）
- G-03: 首屏加载时间 ≤ 2秒（P95）
```

**修复建议**：
- 每个目标必须有「指标名称 + 目标值 + 当前值」
- 使用SMART原则：具体(Specific)、可衡量(Measurable)、可达成(Achievable)、相关(Relevant)、有时限(Time-bound)

---

### 1.3 非目标缺失或随意

**识别特征**：
- 没有非目标章节
- 非目标内容与核心功能高度相关
- 缺少排除原因说明

**案例**：
```markdown
❌ 错误示例：
非目标：无

✅ 正确示例：
非目标：
| 项目 | 排除原因 |
|------|----------|
| 预约功能 | 需独立评审，本期仅实现现场取号 |
| 多店铺管理 | 属于商家端功能，放至二期 |
| 历史数据分析 | 数据基础设施尚未就绪 |
```

**修复建议**：
- 列出3-5项明确不在本期范围内的内容
- 说明排除原因，帮助团队理解决策背景
- 避免将核心功能误标为非目标

---

## 二、逻辑性漏洞

### 2.1 用户故事与功能需求脱节

**识别特征**：
- US数量远多于FR数量（场景冗余）
- FR无法追溯到具体的US（功能无依据）
- US优先级与FR优先级不一致

**案例**：
```markdown
❌ 错误示例：
US-01（P0）：作为顾客，我希望扫码取号
US-02（P1）：作为顾客，我希望查看排队进度

FR-01：实现扫码入口（未标注对应US）
FR-02：显示门店信息（未标注对应US）

✅ 正确示例：
US-01（P0）：作为顾客，我希望扫码快速取号
  └─ FR-01: 扫码入口实现
  └─ FR-02: 取号接口调用
  └─ FR-03: 服务通知推送

US-02（P1）：作为顾客，我希望查看排队进度
  └─ FR-04: 实时进度查询
```

**修复建议**：
- 每个FR必须关联至少一个US
- US优先级决定FR优先级（US降级时，关联FR需重新评估）
- 使用表格或结构化方式清晰展示US→FR映射

---

### 2.2 验收标准不可测试

**识别特征**：
- 使用「体验好」「界面美观」等主观描述
- 缺少前置条件和预期结果
- 无法判断「通过」还是「不通过」

**案例**：
```markdown
❌ 错误示例：
FR-01: 实现取号功能
验收标准：功能正常，用户体验好

✅ 正确示例：
FR-01: 扫码入口实现
验收标准：
1. 扫描门店二维码后，5秒内显示取号页面
2. 门店二维码携带门店ID参数，支持多门店区分
3. 二维码失效（如门店已下线）时，提示「门店不存在」
```

**修复建议**：
- 验收标准必须是可以「Yes/No」判断的
- 包含前置条件（当...时）、操作（执行...）、预期结果（显示/返回...）
- 覆盖正常、异常、边界场景

---

### 2.3 成功指标与目标不对应

**识别特征**：
- 指标无法反映目标达成情况
- 缺少数据来源或计算方法
- 指标与目标量纲不一致

**案例**：
```markdown
❌ 错误示例：
目标 G-02：放弃等候率降低至15%

成功指标：
- 指标：接口调用次数（日均10万次）❌ 不对应
- 指标：系统可用性（99.9%）❌ 不对应

✅ 正确示例：
目标 G-02：放弃等候率降低至15%（当前35%）

成功指标：
- 领先指标：自助取号使用率 ≥ 70%（数据来源：埋点，公式：自助取号数/总取号数）
- 滞后指标：放弃等候率 ≤ 15%（数据来源：门店统计，公式：过号未重排数/总取号数）
```

**修复建议**：
- 每个目标至少对应1个领先指标 + 1个滞后指标
- 明确数据来源（埋点、系统报表、人工统计）
- 提供计算公式或定义

---

## 三、完整性漏洞

### 3.1 用户角色覆盖不全

**识别特征**：
- 只有顾客视角，没有商家/管理员视角
- 缺少异常情况下的用户角色
- 遗漏跨角色协作场景

**常见遗漏角色**：
- 管理员/运营人员
- 客服人员
- 门店店员
- 系统管理员

**修复建议**：
- 梳理所有相关用户角色
- 识别每个角色的核心诉求
- 补充跨角色协作的US（如：顾客取号→店员叫号→顾客被叫）

---

### 3.2 异常流程缺失

**识别特征**：
- 只有主流程描述
- 没有网络异常、超时、失败的处理
- 缺少边界条件（如库存为0、排队满员）

**常见遗漏场景**：
| 场景 | 缺失风险 |
|------|----------|
| 网络断开 | 用户以为操作成功，实际失败 |
| 接口超时 | 无限等待，用户体验差 |
| 并发冲突 | 库存超卖、排队号重复 |
| 权限不足 | 用户看到不属于自己的数据 |
| 依赖服务不可用 | 整体功能不可用 |

**修复建议**：
- 每个关键FR必须包含异常流程的US
- 使用「正常流程/异常流程/边界条件」三段式描述

---

### 3.3 状态定义缺失

**识别特征**：
- 涉及流程审批、订单等状态机功能时
- 没有明确的状态定义
- 缺少状态流转图

**案例**：
```markdown
❌ 错误示例：
FR-05: 排队状态管理
验收标准：能够管理排队状态

✅ 正确示例：
FR-05: 排队状态管理
状态定义：
- 等待中：顾客取号后，等待叫号
- 已叫号：当前被叫，等待用户确认
- 已服务：用户已到场，业务完成
- 已过号：超时未响应，移至队尾或失效

状态流转：
等待中 → 已叫号（店员发起叫号）
已叫号 → 已服务（用户确认到场）
已叫号 → 已过号（超时3分钟无响应）
已过号 → 等待中（用户选择重新排队）
```

**修复建议**：
- 涉及状态机的功能，定义所有可能状态
- 明确状态流转条件和触发动作
- 必要时附状态流转图

---

## 四、可执行性漏洞

### 4.1 依赖项不明确

**识别特征**：
- 依赖外部系统但未说明
- 缺少依赖方的确认
- 没有约定接口规范

**修复建议**：
- 列出所有依赖项（团队、系统、第三方服务）
- 标注依赖方负责人
- 约定接口规范或文档链接
- 设置依赖交付的 deadline

---

### 4.2 开放问题无期

**识别特征**：
- 开放问题没有负责人
- 没有期望答复时间
- 问题长期悬空未解决

**修复建议**：
- 每个开放问题必须有「负责人 + 期望答复时间」
- 定期跟踪，在评审会回顾
- 问题关闭后才能进入开发阶段

---

### 4.3 时间计划不合理

**识别特征**：
- 里程碑之间时间间隔不合理
- 没有考虑依赖和评审时间
- 缺少 buffer

**修复建议**：
- 考虑节假日、评审周期
- 留有 buffer（建议 10-15%）
- 与开发团队确认工时可行性

## 五、反推 Skill 改进建议

基于以上常见漏洞类型，提出对 `chen-prd-skills` 的改进方向：

### 5.1 流程改进

| 当前流程 | 改进建议 |
|----------|----------|
| 书写 → 评审 | 增加「自检清单」环节，作者先自查33项检查点 |
| 单人书写 | 建议多角色参与（产品+研发+测试）|
| 评审一次性 | 分阶段评审（结构评审 → 逻辑评审 → 细节评审）|

### 5.2 文档补充

| 补充内容 | 说明 |
|----------|------|
| 漏洞案例库 | 整理常见错误案例，正反对照 |
| 指标库 | 常见业务指标的定义和计算公式 |
| 角色模板 | 不同类型产品的常见用户角色清单 |

### 5.3 模板优化

| 当前模板 | 优化方向 |
|----------|----------|
| 验收标准无格式 | 增加「条件-操作-结果」格式引导 |
| 目标无格式 | 增加「指标名+目标值+当前值」格式引导 |
| 无自检提示 | 增加「自检已完成□」勾选框 |
