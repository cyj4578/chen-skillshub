# PRD 书写指南与避坑手册

> 本文档基于 `chen-te-skills` 审查实践中发现的常见问题，总结书写要点和避坑建议。

---

## 一、问题陈述书写要点

### 1.1 常见错误

| 错误类型 | 示例 | 问题 |
|----------|------|------|
| 无数据支撑 | 「用户反馈体验不好」 | 缺乏说服力 |
| 模糊描述 | 「效率低下」「体验差」 | 无法量化改进效果 |
| 缺少背景 | 「需要开发XX功能」 | 决策依据不足 |

### 1.2 正确写法

```
问题陈述 = 用户/场景 + 具体痛点 + 影响/损失 + 数据支撑

模板：
目前 [用户/场景] 面临 [具体问题]，导致 [负面影响]。
根据 [数据来源]，约有 [X%] 的用户遇到此问题，
平均每次 [损失/耗时] [Y]。如果不解决，将影响 [业务目标]。
```

### 1.3 数据来源推荐

| 数据类型 | 推荐来源 |
|----------|----------|
| 用户调研 | 访谈记录、问卷统计 |
| 行为数据 | 埋点数据、后台日志 |
| 业务数据 | 订单/营收报表 |
| 客服反馈 | 工单系统、投诉记录 |

## 二、目标书写要点

### 2.1 常见错误

| 错误类型 | 示例 | 问题 |
|----------|------|------|
| 模糊动词 | 「提升」「改善」「优化」| 无法衡量 |
| 无数值 | 「降低流失率」| 降到多少？ |
| 与业务目标脱节 | 「提升系统性能」| 有什么用？ |

### 2.2 SMART 原则检查

| 维度 | 要求 | 检查问题 |
|------|------|----------|
| S - Specific（具体） | 目标明确，不模糊 | 「降低流失率」→「降低顾客放弃等候率」 |
| M - Measurable（可衡量）| 有明确数值 | 有目标值和当前值吗？ |
| A - Achievable（可达成）| 有实现路径 | 技术上可行吗？ |
| R - Relevant（相关）| 与业务目标对齐 | 能支撑业务目标吗？ |
| T - Time-bound（有时限）| 有衡量时间节点 | 什么时候验收？ |

### 2.3 正确写法

```
目标 = 业务动作 + 衡量指标 + 目标值 + 当前值

示例：
G-01: 提高取号效率
     - 衡量指标：顾客平均自助取号耗时
     - 目标值：≤ 15秒
     - 当前值：45秒（人工登记）
     - 衡量时间：上线后 7 天
```

## 三、用户故事书写要点

### 3.1 标准格式

```
作为 <用户角色>，我想要 <功能>，以便 <获得价值>
```

### 3.2 常见错误

| 错误类型 | 示例 | 问题 |
|----------|------|------|
| 缺少角色 | 「需要实现XX功能」| 谁要用？ |
| 缺少价值 | 「作为用户，我要登录」| 登录干什么？ |
| 功能描述代替用户故事 | 「作为用户，我要点击按钮」| 过于技术化 |
| 多个功能堆在一起 | 「作为用户，我要登录、查看、下单」| 一个故事做多件事 |

### 3.3 正确写法

```
❌ 错误：作为用户，我要登录

✅ 正确：
作为顾客，我想要使用微信一键登录，以便无需注册直接使用

❌ 错误：作为用户，我要查看订单列表、订单详情、取消订单

✅ 正确（拆分为多个故事）：
- US-01：作为顾客，我想要查看订单列表，以便了解历史购买记录
- US-02：作为顾客，我想要查看订单详情，以便了解物流进度
- US-03：作为顾客，我想要取消订单，以便取消不想要的商品
```

### 3.4 验收标准格式

采用「条件-操作-结果」格式：

```
验收标准格式：<前置条件> 时，<操作>，<预期结果>

示例：
1. 扫描门店二维码后，5秒内显示取号页面
2. 点击「立即取号」后，显示当前排队号码和预计等待时间
3. 取号成功后，收到微信服务通知
```

## 四、功能需求书写要点

### 4.1 US→FR 映射

每个 FR 必须能追溯到对应的 US：

```
US-01 → FR-01（扫码入口）
      → FR-02（取号接口）
      → FR-03（服务通知）

US-02 → FR-04（进度查询）
```

### 4.2 验收标准要求

| 要求 | 说明 |
|------|------|
| 可验证 | 能判断「通过」还是「不通过」|
| 可重复 | 同一条件多次测试结果一致 |
| 有边界 | 覆盖正常/异常/边界场景 |

### 4.3 常见错误

| 错误类型 | 示例 | 问题 |
|----------|------|------|
| 主观描述 | 「界面美观」「体验流畅」| 无法测试 |
| 功能堆砌 | 「实现XX功能，包括ABC」| 太笼统 |
| 缺少异常处理 | 只描述正常流程 | 异常情况未覆盖 |

## 五、常见漏洞自检清单

### 5.1 结构完整性

- [ ] 封面信息完整（标题/编号/版本/作者/日期）
- [ ] 问题陈述有数据支撑
- [ ] 目标包含「指标+目标值+当前值」
- [ ] 非目标有排除原因

### 5.2 逻辑一致性

- [ ] US 有验收标准
- [ ] FR 有验收标准
- [ ] 每个 US 至少有一个 FR 对应
- [ ] 成功指标能反映目标达成

### 5.3 需求完整性

- [ ] 核心用户角色都有 US
- [ ] 正常/异常/边界场景都有描述
- [ ] 状态机有状态定义和流转图

### 5.4 可测试性

- [ ] 验收标准可以「Yes/No」判断
- [ ] 成功指标有数据来源
- [ ] 时间计划有明确交付物

## 六、书写顺序建议

| 顺序 | 章节 | 耗时占比 | 说明 |
|------|------|----------|------|
| 1 | 问题陈述 | 15% | 明确「为什么做」|
| 2 | 目标 | 15% | 明确「做到什么」|
| 3 | 非目标 | 5% | 明确「不做什么」|
| 4 | 用户故事 | 25% | 描述「谁要什么」|
| 5 | 功能需求 | 25% | 拆解「怎么做」|
| 6 | 其他章节 | 15% | 完善细节 |
